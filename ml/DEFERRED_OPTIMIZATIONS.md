# Отложенные оптимизации ML-сервиса

Список улучшений, оставшихся после реализации топ-5 быстрых побед
(см. PR с Win 1–5: async-подписи, кэш декодированных изображений,
даунсэмплинг качества, батчинг CLIP + auto-device, переиспользуемые S3-клиент
и thread pool).

Пункты сгруппированы по разделам и упорядочены по убыванию ожидаемого эффекта
внутри каждой группы.

---

## Производительность пайплайна

### 1. ONNX Runtime + int8-квантование CLIP

**Что:** Сконвертировать ViT-B/32 из PyTorch CPU в ONNX Runtime и применить
динамическое int8-квантование. Подменить `clip.load(...)` обёрткой, отдающей
ONNX-сессию вместо `torch.nn.Module`.

**Зачем:** ViT-B/32 на CPU — самая дорогая часть пайплайна (~50–100 мс на
фото). ONNX Runtime + int8 даёт 2–4× ускорение без существенной потери
качества для подобной задачи (классификация/похожесть).

**Сложность:** средняя. Нужно сохранить совместимость с
`preprocess` из upstream-`clip` (это просто torchvision-трансформы) и заменить
`encode_image` / `encode_text` на запуск ONNX-сессии. Тесты уже мокаются
вокруг `model.encode_image(batch)` — интерфейс выдержит подмену.

**Связанные файлы:** `app/pipeline/embeddings.py`, `app/pipeline/reranker.py`.

### 2. Job-модель для `/process`

**Что:** Сделать обработку асинхронной на уровне HTTP-API:
- `POST /process` → возвращает `{ "job_id": "..." }` мгновенно
- `GET /jobs/{id}` → отдаёт `pending | running | done | failed` + результат

Очередь — Redis/Celery, либо `asyncio.Queue` + воркеры в той же
инстанции для MVP.

**Зачем:** Текущий `/process` синхронен и идёт 30–60 с в худшем случае —
ломаются прокси-таймауты, повторы клиента и UX. Для очереди тяжёлых
ML-задач это анти-паттерн.

**Сложность:** высокая. Затрагивает API-контракт, мобильный клиент и
хранилище состояний.

**Связанные файлы:** `app/main.py`, `app/schemas.py` (нужен `JobResponse`),
новые модули `app/jobs.py` или `app/worker.py`.

---

### 3. Лимит конкурентности на уровне приложения

**Что:** Ограничить одновременную обработку запросов:
```python
_PIPELINE_SEMAPHORE = asyncio.Semaphore(2)

@app.post("/process")
async def process(...):
    async with _PIPELINE_SEMAPHORE:
        ...
```
Альтернативно — через `uvicorn --limit-concurrency 4`.

**Зачем:** Два-три параллельных запроса с большими альбомами легко уронят
процесс по памяти (декодированные PIL.Image в RAM + CLIP-батчи).

**Сложность:** низкая.

**Связанные файлы:** `app/main.py`.

---

### 4. Сборка cover-caption параллельно с подписями страниц

**Что:** `generate_cover_caption` сейчас запускается отдельным round-trip
после `generate_captions`. Можно объединить в один `asyncio.gather`,
сэкономив 0.5–1.5 с на каждый запрос.

**Зачем:** мелочь, но «бесплатная».

**Сложность:** низкая.

**Связанные файлы:** `app/pipeline/__init__.py`, возможно небольшой
рефакторинг в `cover_filler.py`.

## Корректность и UX

### 5. Валидация `min_photos ≤ len(photo_ids)` на уровне `ProcessRequest`

**Что:** Сейчас проверка живёт в `_run_pipeline_sync` и срабатывает только
после S3-скачивания. Перенести в `@model_validator(mode="after")`.

**Зачем:** Если клиент послал 5 photo_ids c `min_photos=10`, мы тратим
S3-трафик и время на скачивание прежде чем вернуть 422.

**Сложность:** тривиальная.

**Связанные файлы:** `app/schemas.py`.

---

### 6. Воспроизводимый quality score (без min-max в пределах батча)

**Что:** Сейчас `score_quality` нормирует sharpness в пределах одного
запроса — одно и то же фото получает разные скоры в зависимости от соседей.
Перейти на абсолютный масштаб, например `log(sharpness + 1)` с фиксированной
шкалой и порогом для exposure.

**Зачем:** Воспроизводимость + кэш-возможность (можно закэшировать score
по photo_id, если фото загружено повторно).

**Сложность:** низкая, но требует подбора коэффициентов на реальных
данных.

**Связанные файлы:** `app/pipeline/quality.py`.

---

### 7. `available.pop(0)` в `fill_template` — заменить на deque/индекс

**Что:** В `template_filler.py:37` используется `list.pop(0)` — O(n) на
каждом слоте → O(n²) на больших шаблонах.

**Зачем:** На альбомах с 50+ слотами уже заметно.

**Сложность:** тривиальная.

**Связанные файлы:** `app/pipeline/template_filler.py`.

## Архитектурные улучшения

### 8. `asyncio.get_event_loop()` → `get_running_loop()`

**Что:** `pipeline/__init__.py` использует `asyncio.get_event_loop()` —
устаревшее в 3.10+ предупреждает в логах.

**Сложность:** тривиальная.

**Связанные файлы:** `app/pipeline/__init__.py`.

---

### 9. Чистый split sync/async в pipeline

**Что:** Сейчас `_run_pipeline_sync` возвращает `_PipelineState`, и async-часть
вызывает captions/covers сверху. Логика «выбрать backend по ключам» дублирована
в `_resolve_caption_backend`. Подумать про вынос всего LLM-шага в отдельный
сервис-объект `CaptionService`, который инжектится через DI.

**Зачем:** Тестируемость и возможность подменить бэкенд (например, локальная
LLaMA через Ollama).

**Сложность:** средняя.

---

### 10. Отделить `_OPENROUTER_BASE_URL` от модуля captions

**Что:** Константа `_OPENROUTER_BASE_URL` живёт приватно в
`caption_generator.py` и импортируется в pipeline и cover_filler как leaky
абстракция. Перенести в `config.py` как публичное поле `Settings`.

**Сложность:** тривиальная.

**Связанные файлы:** `app/config.py`, `app/pipeline/caption_generator.py`,
`app/pipeline/__init__.py`.

---

### 11. Освобождать память после стадий

**Что:** Сейчас `images: dict[str, PIL.Image]` живёт всю сессию пайплайна,
включая стадии после `extract_embeddings` (≈250–500 МБ на 50 фото высокого
разрешения). Можно:
- После `score_quality` убрать из cache те фото, что не попали в `selected`
- Вместо PIL.Image хранить bytes JPEG-thumbnail (если нужны только подписи)

**Зачем:** Снижает пик памяти ≈3×.

**Сложность:** средняя — нужна аккуратность с тем, какие фото нужны
captions/covers (только из `ranked`, не все).

**Связанные файлы:** `app/pipeline/__init__.py`, `app/pipeline/image_cache.py`.

---

### 12. Структурное логирование

**Что:** Сейчас `logging.basicConfig(level=...)` без форматтера. Под
prod-нагрузкой потребуются структурированные логи (JSON) с trace_id —
каждый запрос проходит много стадий, логи без контекста тяжело
анализировать.

Использовать `structlog` или `python-json-logger`. Контекст: photo_count,
template_id, продолжительность каждой стадии.

**Сложность:** низкая.

**Связанные файлы:** `app/main.py`, во всех модулях `pipeline/`.

---

### 13. Метрики Prometheus / OpenTelemetry

**Что:** Добавить histograms по стадиям пайплайна (download, embed, cluster,
quality, llm), счётчики ошибок и `up`-метрику.

**Зачем:** Без метрик невозможно понимать, где затыки в проде.

**Сложность:** низкая (есть готовые middleware для FastAPI).

## Прочее

### 14. Streaming-чтение из S3

**Что:** Сейчас `obj["Body"].read()` читает весь файл целиком в память.
Для очень больших файлов спайк по памяти. Альтернатива — прокинуть `Body`
прямо в `Image.open` (PIL умеет читать file-like).

**Сложность:** низкая.

**Связанные файлы:** `app/pipeline/s3_loader.py`.

---

### 15. Чанкинг preprocess в embeddings параллельно с CLIP forward

**Что:** Сейчас сначала делаем `preprocess(img)` для всех изображений,
потом батчево скармливаем в CLIP. Можно конвейеризировать: пока CLIP
считает батч N, в отдельном потоке готовится батч N+1.

**Сложность:** средняя (надо аккуратно с GIL и cuda streams).

**Связанные файлы:** `app/pipeline/embeddings.py`.

---

### 16. Кэш CLIP-эмбеддингов по photo_id

**Что:** Если клиент повторно прислал тот же photo_id (например, перегенерация
альбома), не пересчитывать эмбеддинг. Простой LRU по hash(bytes) или
photo_id (с TTL).

**Зачем:** Существенное ускорение для повторных запросов с пересечением
по photo_ids.

**Сложность:** средняя — нужно хранилище (Redis/in-memory с инвалидацией).
